## S4: Paho MQTTv5 1.2.5 under R8 on API 24 and 30

Broker: `/Users/danielstoyanoff/dev/homelab/services/smart-home/mqtt.yaml` defines Mosquitto (`eclipse-mosquitto:2`, `listener 1883`, `allow_anonymous true`) behind a **ClusterIP** service `mqtt` in namespace `smart-home`. There is no LoadBalancer IP and no `mqtt.lan` ingress (only `zigbee2mqtt.lan` for the web UI), and `kubectl` could not reach the API (`127.0.0.1:26443` refused). So the real broker was **not reachable from the devices' subnet**. Substitute: `eclipse-mosquitto:2` (2.1.2, same config) in Docker on the Mac at `10.0.0.114:18830`; both devices reach it (ping, TCP). The container was removed afterwards.

## Bring-up findings 2026-10-19

First hours on the wall (X1, Android 7):

- **Proximity never reaches apps on the X1.** The HAL logs `ProximitySensor: unknown event (type=3, code=0)`; only the stock app, running as system, sees the events. X1 night mode is therefore touch-to-wake only.
- **The stock app's auto-brightness, idle-off and dim must be disabled by the user in the Shelly UI**, or they fight the kiosk for the backlight (it can write the sysfs node; the kiosk now treats a lit panel it thought dark as a wake).
- **ShellyElevate writes its fixed brightness (255) on its own start**, even with `automaticBrightness` off. The X1's light sensor reports on change only, so after a (re)start no lux arrives until the light changes; the kiosk applies the last level it wrote (or the minimum) after 500 ms and lets the first reading take over.
- Waking the panel started `DashboardActivity` from the service (`START ... from uid` 16 ms after the touch). The wake path now only starts it when it is not the resumed activity.
- Five taps on the status dot do not work (the health popover opens on the first tap and its scrim takes the rest); the settings gesture is the status dot held for 5 s. It is the only settings gesture (the two-finger hold is gone); provisioning can still open the sheet with `am start --es settings true`.
- **After a reboot the stock Shelly app took the dashboard down with it (X1, three reboots).** `BootReceiver` started `KioskService` at about +70 s, and 2 s later keep-in-front launched the dashboard right inside the stock app's own start-up (`cloud.shelly.stargate` `SplashActivity` at +66 s, `SHELLY_APPLICATION_INIT`). The stock app then logged `SHELLY APPLICATION SHUTDOWN COMPLETED`, our process vanished and the package was left `stopped=true` (force-stopped, the caller not in the log); nothing of ours ran again until an `am start`. Started by hand at +130 s, after the stock app had settled, the dashboard stayed in front and survived the stock app re-initialising. ShellyElevate's activity is not stopped (it starts immediately).
  - Fix: on the Shelly profiles, a boot start (the receiver passes an extra) holds the dashboard back (`BootGate`) until the top activity has been stable for `KioskConfig.bootSettleMs` (30 s; the splash resets it) and at least `bootMinMs` (90 s) have passed since boot, whichever is later; the service runs meanwhile (MQTT, sensors). Logged at error level: `boot: waiting for the stock app to settle`, `boot: settled, taking the front`. Separately, `FrontDecision.shouldLaunch` never launches while the stock splash is on top, on any boot; the next tick tries again. `Generic` is unchanged.
  - Resilience: a one-shot alarm (`WatchdogReceiver`, 60 s ahead, pushed back by healthy ticks) restarts the service if our process is killed outside a force-stop; the service was already `START_STICKY`. A **force-stopped package cannot recover itself**: the system drops its alarms and receivers until something starts it by hand, so it needs `am start` or a re-provision (the CLI's `deploy` does that). The boot timing is to be confirmed on the X1 after merge.

## Decision: system install on the X1 (2026-10-19)

The X1 is a userdebug image, and the stock app force-stops every non-system app at each boot, so the dashboard app is installed as a system app there: `hashsome android provision --system` (ShellyElevate's `install-privapp.sh` procedure: `adb root`, remount `/system` read-write, `/system/priv-app/Hashsome/Hashsome.apk`, 755/644 `root:root`, `restorecon`, remount read-only, reboot; Apache-2.0, `android/NOTICE`). Optional and Shelly-only: a tablet keeps the normal install, and the X2i (a user build) cannot. The permissions and settings broadcast run after the reboot (a priv-app is unknown to the package manager until the boot scan). Nothing is recorded in `devices.json`; later updates are a plain `deploy`, `uninstall --system` undoes it. Not yet run on a device; the bring-up on the X1 confirms it.

Boot gate as a system app (2026-10-19): the stock app's force-stop hook skips system apps, so with `provision --system` the long gate (30 s settle, 90 s minimum) only delayed the dashboard by about two minutes after a power cycle, with the stock UI showing meanwhile; a first cut with a 5 s settle still left the stock app visible too long. When the app runs with `ApplicationInfo.FLAG_SYSTEM` (also set for an updated system app), there is now no gate at all: `BootGate` is open from the start (logged as `boot: system app, no gate`) and `shouldLaunch` no longer holds back over the stock Splash, so launching over it is harmless and keep-in-front retakes the front 2 s after the stock app's own restart covers us. A non-system install keeps the conservative gate and the Splash guard; it still cannot survive the hook, but the gate is harmless. To be confirmed on the X1 after a power cycle.

## Early boot start (2026-10-19)

Goal: the dashboard as early after boot as the system allows (measured: `Displayed DashboardActivity` about 8 s after the stock app's init). `BootReceiver` now handles `LOCKED_BOOT_COMPLETED` as well as `BOOT_COMPLETED`, is `directBootAware`, and both filters carry `android:priority="999"`. The first broadcast that finds the user unlocked starts `KioskService` (`Kiosk.startService(boot = true)`); a process-level flag (`BootStart.claim`) makes the later one a no-op, and the service's `rebuilder == null` check covers a second `onStartCommand` anyway. Logged at error level, tag `boot`: which action started it and the elapsed ms since boot.

Direct-boot storage: `Settings` stays in normal (credential-encrypted) SharedPreferences. It is not migrated to device-protected storage (`moveSharedPreferencesFrom` would move the prefs of every display already provisioned, and `Settings.init` runs on every process start, so a failed move leaves a display with defaults). Instead, when `UserManager.isUserUnlocked` is false the receiver does nothing and waits for `BOOT_COMPLETED`, and `KioskExtension.install` (run by `Application.onCreate`, which a direct-boot start also creates) defers its work to `ACTION_USER_UNLOCKED`, because reading CE preferences while locked throws. The displays have no lock screen, so the user is normally unlocked at `LOCKED_BOOT_COMPLETED` and nothing waits. `DashboardActivity` is not direct-boot aware and is started by the service as soon as it runs (the keep-in-front tick, no boot gate for a system app since #168), so the dashboard comes as early as the service does. To be confirmed on the X1.
