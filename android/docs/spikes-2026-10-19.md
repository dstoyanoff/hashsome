## Gaps (read first)

- **Nobody was in the bathrooms, so no real proximity wave and no real finger touch could be produced.** "Proximity wakes the screen" and "touch while dark" are UNVERIFIED on both devices. What was verified: the sensors are registered and `active` in `dumpsys sensorservice` while the display is off, both report `isWakeUpSensor=true`, and the wake lock path (what the proximity handler calls) works. `adb shell input tap` is injected and not representative. To finish it: install the APK, `lock`, `wake-on-proximity on`, wave a hand, read `adb logcat -s spike`.
- `screencap` shows the framebuffer, not the backlight, so "visibly dark" cannot be judged remotely. For X1, sysfs 0 is the path ShellyElevate itself uses for "off".
- The cluster API (`127.0.0.1:26443`) was unreachable, so the real Mosquitto was not tested (see S4).
- **Logging gotcha:** on the X1 (MT6580) `getprop log.tag` is `E`, and `Log.i/d/w` from apps never reach logcat. Only `Log.e` does. Remember this when debugging the kiosk on the X1.

## S4: Paho MQTTv5 1.2.5 under R8 on API 24 and 30

Broker: `/Users/danielstoyanoff/dev/homelab/services/smart-home/mqtt.yaml` defines Mosquitto (`eclipse-mosquitto:2`, `listener 1883`, `allow_anonymous true`) behind a **ClusterIP** service `mqtt` in namespace `smart-home`. There is no LoadBalancer IP and no `mqtt.lan` ingress (only `zigbee2mqtt.lan` for the web UI), and `kubectl` could not reach the API (`127.0.0.1:26443` refused). So the real broker was **not reachable from the devices' subnet**. Substitute: `eclipse-mosquitto:2` (2.1.2, same config) in Docker on the Mac at `10.0.0.114:18830`; both devices reach it (ping, TCP). The container was removed afterwards.

| Check                               | Result                                                                                                                                                                                      |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Build                               | `assembleRelease` with `isMinifyEnabled` and `isShrinkResources` on succeeds with no R8 missing-class errors with the default rules.                                                        |
| **Runtime under R8, no keep rules** | **Fails**: `java.util.MissingResourceException: Error locating the logging class` (Paho loads `JSR47Logger` by name).                                                                       |
| Keep rule that fixes it             | `-keep class org.eclipse.paho.mqttv5.client.logging.JSR47Logger { <init>(); }`. No other rule was needed.                                                                                   |
| Jenna (API 30), awake and dark      | connect 331-343 ms, subscribe, retained `hello` published and received, **round trip 9-14 ms**, retained cleared.                                                                           |
| Stargate (API 24), awake and dark   | connect 466-657 ms, round trip **22 ms (awake), 81 ms (display off)**, retained cleared.                                                                                                    |
| Cleanup                             | Topic `hashsome/spike/<device>`; each run publishes an empty retained payload at the end. `mosquitto_sub` afterwards saw no retained message. Nothing was published under `homeassistant/`. |
| Gotcha                              | Paho v5 against an MQTT 3.1.1-only broker fails with `Invalid Return code (50001)`. (Mosquitto 2 speaks v5, so the real broker is fine.)                                                    |

Verdict: Paho MQTTv5 works on API 24 and 30 under R8 with the single keep rule above; no minimal-client fallback needed.

## Bring-up findings 2026-10-19

First hours on the wall (X1, Android 7):

- **Proximity never reaches apps on the X1.** The HAL logs `ProximitySensor: unknown event (type=3, code=0)`; only the stock app, running as system, sees the events. X1 night mode is therefore touch-to-wake only.
- **The stock app's auto-brightness, idle-off and dim must be disabled by the user in the Shelly UI**, or they fight the kiosk for the backlight (it can write the sysfs node; the kiosk now treats a lit panel it thought dark as a wake).
- **ShellyElevate writes its fixed brightness (255) on its own start**, even with `automaticBrightness` off. The X1's light sensor reports on change only, so after a (re)start no lux arrives until the light changes; the kiosk applies the last level it wrote (or the minimum) after 500 ms and lets the first reading take over.
- Waking the panel started `DashboardActivity` from the service (`START ... from uid` 16 ms after the touch). The wake path now only starts it when it is not the resumed activity.
- Five taps on the status dot do not work (the health popover opens on the first tap and its scrim takes the rest); the settings gesture is the status dot held for 5 s. It is the only settings gesture (the two-finger hold is gone); provisioning can still open the sheet with `am start --es settings true`.
